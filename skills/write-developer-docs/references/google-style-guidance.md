# Google style guidance

This is a selective, paraphrased adaptation of the [Google developer documentation style guide](https://developers.google.com/style), verified on 2026-09-10. It is not an official Google publication or a complete copy. Google's documentation is licensed under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/), except where otherwise noted. Examples in the companion document-patterns reference are original.

Use project-specific style before this guidance. Google treats its recommendations as adaptable: choose clarity for the actual audience and remain consistent. The skill's workflow, document patterns, and verification requirements are local practices, not claims about Google mandates.

## Everyday writing

- Use a friendly, direct, respectful voice. Prefer familiar words; avoid marketing language, slang, idioms, and unnecessary formality. Do not describe a task as easy or obvious.
- Make the actor and action clear. Use active voice where it clarifies responsibility and address the reader as “you” in instructions.
- Use consistent terms for the same concept. Explain unfamiliar technical terms and abbreviations without weakening their meaning.
- Default to American English spelling and serial commas unless project conventions or the request specify otherwise.
- Place a condition before the instruction it governs so readers can decide whether the action applies.

Sources: [Highlights](https://developers.google.com/style/highlights), [Voice and tone](https://developers.google.com/style/tone).

## Structure and procedures

- Use descriptive sentence-case headings and a logical hierarchy without skipped levels. Use action phrases for tasks and noun phrases for concepts. Retain proper capitalization of product names and identifiers.
- Use numbered steps when order matters and bullets for unordered items. Keep a single-step instruction simple rather than adding an artificial numbered sequence.
- Provide prerequisites before the procedure. Name the environment or tool before the action when readers need that context.
- Keep each step focused on an action or reader decision. Introduce commands by their purpose, define placeholders, and explain results when needed for the next action or to recognize completion.
- Mark optional actions explicitly. Put results after their actions and separate alternate procedures when both are needed.
- Keep essential instructions in the main flow instead of hiding them in notes.

Sources: [Headings and titles](https://developers.google.com/style/headings), [Procedures](https://developers.google.com/style/procedures).

## Formatting and comprehension aids

- Format code identifiers as code and UI labels in bold; preserve their exact spelling. Use language-tagged code blocks when the destination supports them.
- Make examples relevant to the nearby explanation. Separate input from output and identify values readers must replace.
- Use descriptive link text that communicates the destination or purpose.
- Use a table when readers need to compare related attributes; use a list or prose for a simple sequence or explanation. Provide meaningful column headings.
- Use semantic headings and lists, useful image text alternatives, and explanations that do not depend solely on color, screen position, or an image. Keep important meaning available in text.

Sources: [Code samples](https://developers.google.com/style/code-samples), [Highlights](https://developers.google.com/style/highlights), [Tables](https://developers.google.com/style/tables), [Accessible documentation](https://developers.google.com/style/accessibility).

## Targeted lookup

Do not apply Android- or Google Cloud-specific rules to unrelated products.
